# How Aleph works

```text
app.ts ──@aleph/sdk──▶ manifest.json ──aleph-core──▶ validated plan ──▶ execute(tenant, request)
                                       (types, scopes,               (one optimistic transaction,
                                        worst-case cost)              metered, tenant-prefixed keys)
```

## 1. You describe, the SDK records

Handlers in `@aleph/sdk` are ordinary TypeScript functions that run **once, at build time**, with symbolic values. Calling `Task.get(...)` doesn't read anything. It appends a `get` operation to the route's plan and returns an accessor whose fields are expressions. `a.plus(b)` records an addition, `$.when(cond, ...)` records a branch, and `list.map(...)` records a bounded loop.

So control flow uses `$` helpers, not native `if` or `for`: native statements run once, at build time. The SDK throws when an expression is used as a plain JavaScript value, which catches most of these mistakes.

## 2. The manifest is the program

The build produces a **manifest**: versioned JSON that lists:
- entities, counters, routes, handlers, and workflows
- their plans

A plan is a tree of statements, operations, and expressions from a closed set. No author code ships. The same manifest can be generated by another SDK, or by hand. See [Manifest format](/docs/reference/manifest/).

## 3. The core checks

`aleph-core` is a Rust library. Validation works out a lot about each plan:
- **References:** every entity, field, index, input, error, and step it names exists.
- **Scopes and types:** it resolves variable scopes and infers types, including nullability and string lengths.
- **Worst-case cost:** sequences add, branches take the maximum, and loops multiply by their list's maximum length. The result is compared with the [limits](/docs/reference/limits/).

Diagnostics carry a stable code, a manifest path, and, with source maps, a `file:line:col` in your `app.ts`.

## 4. The core runs

The same crate interprets the validated plan:
- Each request is **one optimistic, serializable transaction**, re-run on conflict.
- A **meter** charges every read, write, and operation, and stops the run at the first charge over a limit. The static analysis says the meter will never trip; the meter makes sure.
- Effects (events, jobs, messages) go to a **transactional outbox**, written in the same commit.
- Every key is built inside the tenant's **keyspace**.

The core compiles to WebAssembly too. `aleph dev`, `aleph test`, and the conformance suite run the exact code a production runtime embeds.

## 5. Two implementations that must agree

Static bounds and the runtime meter are two independent accounts of the same cost. Aleph's test suite checks they agree on every example, every conformance scenario, and more than 100,000 generated plans.
