# Aleph vs. alternatives

## Serverless functions
Functions run arbitrary code per request. You get full flexibility, but you're on your own for transactions, idempotency, isolation, and cost: a function's worst case is unknown until it happens. Aleph trades that flexibility for guarantees the runtime can enforce. Many teams use both: Aleph for the data and rules, a function behind an integration for heavy compute.

## Backend-as-a-service (hosted databases with auth and rules)
These give you storage, auth, and row-level rules. Logic usually ends up in client code or in separate functions, and the cost of a query depends on how it's written. In Aleph the logic lives next to the data in one declaration, every query is bounded by its declared limits, and multi-step work is transactional.

## An ORM with a web framework
The most flexible option, and the most work: you write the transactions, retries, outbox, pagination, validation, docs, and client yourself, and keep them consistent. Aleph generates most of that from one schema. The cost is that you work inside its operation set.

## Workflow engines
Workflow engines make long-running processes durable by replaying code, which forces that code to be deterministic. Aleph workflows are declared as steps, each a bounded transaction with typed state. There's nothing to replay, and determinism is structural instead of a rule you have to follow.

## Infrastructure as code
Tools like Terraform and Pulumi describe infrastructure as data and compute a plan before applying it. Aleph applies the same idea to application logic: describe it, check it, and know what it will do before it runs.
