# Why declarative backends

Most backends are programs. A request runs arbitrary code that can loop, allocate, query, and call out as much as it likes. That flexibility has a cost: nobody can say what a request will do until it does it.

Aleph makes a different trade. A backend is a **description**: routes, entities, and plans built from bounded operations. You give up arbitrary code. In exchange, the system can reason about your backend as a whole.

## What a description makes possible

| Question | In a typical backend | In Aleph |
|---|---|---|
| What's the most a request can read or write? | Unknown until you load-test | Computed from the declarations, before deploy |
| Can a request leave half its writes behind? | Depends on careful transaction handling | Never: one transaction per request |
| Can a retried request send the email twice? | Often, unless you build an outbox | No: effects are released once, after commit |
| Can one customer's request touch another's data? | Only if every query is filtered correctly | It can't name it: keys are tenant-prefixed |
| Does this deploy break existing data or clients? | Found out in production | Classified as safe, backfill, or breaking |
| What does this route return? | Whatever the code returns | An inferred, typed schema |

## Where the cost comes from

The bound of a request comes from your **data declarations**:
- the maximum length of a string field
- the `limit` of a query
- the maximum size of a list input
- the indexes and counters on an entity

Logic only adds, multiplies, and takes maxima of those numbers. Designing the schema is designing the cost model, which is why every `t.string()` needs a `.max(...)`.

## What you give up

- **No unbounded loops.** Loops run over lists with a known maximum length. Work that's unbounded, like processing every row, becomes a scheduled job that walks the data in bounded batches.
- **No arbitrary code in requests.** You compose built-in operations. When you need the outside world, you declare an integration, and the runtime calls it.
- **Per-request limits.** A route reads at most 250 rows and writes at most 50. Bigger work moves to jobs and workflows, each step bounded on its own. See [Limits](/docs/reference/limits/).

These constraints are what make the guarantees possible. The rest of these docs show how far you can get within them.
