# Why declarative

Most backends are programs: a request runs code that can loop, allocate, query, and call out as much as it wants. You find out what it does by running it, under load, in production.

Aleph backends are **descriptions**. You compose a closed set of operations (read this row, query this range of at most 50 rows, send this email after commit), and the composition is data. Data can be inspected before it runs. Everything on this page follows from that.

## Known costs, before deploy

The checker computes each route's worst case from your declarations:
- a string's `.max(...)`
- a query's `limit`
- an array input's maximum length
- the indexes and counters a write must maintain

```text
✖ over_budget at app.ts:41:3 (routes[2].plan)
  route "bulkComplete" can use up to 75 writes in the worst case, over the limit of 50.
  Lower the bounds that drive it (query limits, list sizes) or split the work.
```

You learn about the expensive route when you write it, not when your database falls over. A runtime meter enforces the same bounds while the request runs, so the guarantee holds even if the analysis had a bug. See [Bounded by construction](/docs/bounded-by-construction/).

## Correct by default

Because the runtime knows every operation, it can make the safe thing the only thing:
- every request is one **serializable transaction**
- emails, jobs, and events are released **exactly once**, after commit
- payment-style routes **replay** their response for a repeated idempotency key
- **every key belongs to its tenant**, so one customer's request can't name another's data

You don't write this machinery, and you can't forget it.

## Infrastructure becomes the runtime's problem

A description says what, not how, so the runtime is free to choose the how and improve it:
- **Storage:** key layout, index maintenance, and backfills.
- **Retries:** conflict retries and backoff.
- **Delivery:** the outbox, and how integrations are delivered.
- **Speed:** the runtime itself (the core is Rust).

A faster runtime or a better storage engine underneath doesn't require changing a line of your app.

## Everything else is generated

One declaration drives:
- input validation
- inferred response types
- a typed client
- OpenAPI documents
- MCP tools for agents
- worked examples that run as tests

The schema can be checked against the deployed one before a change ships. All of it stays consistent because there's only one source.

## What you give up

- **No arbitrary code in requests.** You compose built-in operations; the outside world is reached through declared [integrations](/docs/integrations/).
- **No unbounded loops or scans.** Loops run over lists with a known maximum. Work over all your data becomes a [schedule that walks it in batches](/docs/compute/async/).
- **Per-request budgets.** A route reads at most 250 rows and writes at most 50; bigger work moves to jobs and [workflows](/docs/compute/workflows/). See [Limits](/docs/reference/limits/).

These constraints are exactly what buy the guarantees. Most application backends turn out to fit inside them, and the rest of these docs show how.
